### Classification rules

Each row is an auditable workflow or a bounded feature and has exactly one primary status. **Implemented** means sufficient evidence for the named scope, usually local. **Partially implemented** means material portions exist and meaningful workflow pieces remain absent. **Missing** means no meaningful workflow was found. **Broken** means the named behavior conflicts with observable or authoritative evidence. **Needs verification** means code or an integration path exists without sufficient acceptance evidence. **Not applicable** is deliberately outside scope. Related rows can have different statuses when they cover separate outcomes, such as credential entry versus verified merchant activation, or local browser preview versus real-device acceptance. The evidence references and observations specify coverage and its limits. [Status register](FEATURE-IMPLEMENTATION-REGISTER.md)

## Merchant onboarding and financial boundaries

**Current behavior.** An owner saves tenant-specific BCA or Midtrans credentials in Payments. Midtrans verification reads an existing QRIS reference, matches the merchant and checks the dedicated signing key. A protected approval then records independent acceptance of Core API Write and callback evidence. New BCA attempts stay gated pending its approved contract. Connections with history can disable future attempts while retaining encrypted material for reconciliation. The Management register keeps cash and recorded terminal-card tender. [Current workflow](PAYMENTS.md) · [Verification tests](../core/test_priority_merchant_readiness.py)

| Question | Midtrans tenant payments | BCA tenant payments |
| --- | --- | --- |
| How does a business become a merchant? | Use Midtrans registration and the approved product/merchant process. The GoPay onboarding guide directs an existing merchant to its account manager with its Merchant ID. The provider authorizes methods and production access. | QRIS merchant registration and BCA API access are separate provider processes. BCA describes a cooperation application, supporting documents, functional tests and activation for the approved API feature. Verify the applicable contract if Veyra acts as a supporting application provider. |
| Which credential authorization applies? | Veyra uses the legacy Core API Server Key flow today. Midtrans documents permission-scoped Server Keys, a separate notification signing secret, and a distinct BI-SNAP application credential/signing flow. Confirm which contract applies to each approved merchant and environment. | The public BCA SNAP guide describes application credentials, asymmetric authorization and a machine-to-machine access-token exchange followed by signed API requests. Veyra has client and secret inputs but no token exchange or bearer authorization in the QRIS adapter. Confirm the exact approved QRIS service contract with BCA. |
| Can configuration be verified end to end today? | Local simulated charges, retries, callback logic and refunds work. Tenant and platform callbacks support distinct signing credentials in local regressions. Live merchant acceptance remains open. | Controlled transport exercises Veyra’s payload and callback fixtures. Actual BCA authentication, merchant scope, notification and status/cancel contract have not been accepted. Ambiguous local attempts stay blocked pending trusted terminal evidence. |
| Can each business receive its own settlement? | Provider-side settlement and withdrawal can be configured under the merchant’s own contract and bank details. Veyra has no accepted receipt-to-bank payout reconciliation for a real tenant. | The BCA merchant agreement and account govern disbursement. Veyra has no accepted independent BCA merchant settlement proof or bank reconciliation. |

The 28 October 2026 Access Keys change separates notification signing from API authorization. Veyra now uses distinct credentials for each merchant and for platform billing. Both callback handlers preserve trusted status reconciliation. Legacy configurations without a signing field can verify using their original key while teams coordinate migration to the issued Signature Secret Key. Merchant onboarding happens through provider-approved account and product provisioning. [Midtrans Access Keys](https://docs.midtrans.com/docs/access-keys) · [Midtrans onboarding](https://docs.midtrans.com/reference/onboarding-v2) · [Midtrans withdrawal](https://docs.midtrans.com/docs/how-can-i-have-my-money-in-my-account-payout) · [BCA API facility terms](https://www.bca.co.id/-/media/Files/Bisnis/solusi/API/20250718-EBS-0098A-C-2025-ID)

**Separate financial systems.** Tenant checkout has `OrderTender`, `PaymentTransaction`, `PaymentConnection` and `OrderRefund`. It uses the merchant selected for that business. Veyra’s own subscriptions use `BillingInvoice`, `BillingAttempt`, separate platform credentials, an independent callback route and a different reconciliation worker. Sale, refund, merchant payout and SaaS subscription revenue must stay separate in credentials, reports, audit and operator actions.
